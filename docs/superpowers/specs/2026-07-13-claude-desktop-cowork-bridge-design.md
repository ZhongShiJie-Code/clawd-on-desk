# Claude Desktop Code/Cowork bridge

## Goal

Make Claude Desktop Code/Cowork sessions first-class Clawd sessions on macOS:

- show thinking, working, approval-needed, completion, and error states;
- open the originating Claude Desktop window from the HUD/dashboard;
- retain Claude Desktop's native permission UI; and
- route only explicitly installed local/MCP automation through Clawd approval.

The integration must not parse or modify Claude Desktop's private Electron
database, inject into the app, or bypass its own permission decisions.

## Chosen architecture

Claude Desktop already runs Code/Cowork work as `claude --input-format
stream-json --output-format stream-json` processes. Existing Claude Code hooks
remain the event source for prompts, tools, hook errors, and completion. A new
`claude-desktop-bridge` process supplies the missing Desktop identity and focus
metadata.

1. The bridge polls the process table for stream-JSON Claude processes that
   use Desktop's permission-prompt mode, resolves their PID, parent PID, and
   working directory, and creates an `agentId: claude-desktop` state session.
2. It correlates each process with the existing Claude hook session through PID
   metadata. Hook events therefore retain their native tool/state fidelity.
3. When a process exits, the bridge emits an attention/completed state then
   retires the session. It does not infer completion from chat text.
4. Session focus uses the existing macOS focus path to activate `Claude.app`.
   It never attempts to focus a terminal that does not exist.
5. A separate local approval MCP server exposes a `clawd_request_approval`
   tool. Only tools that voluntarily call it are gated by Clawd's permission
   bubble. Native Claude Desktop permission requests remain untouched.

## Data flow

`Claude Desktop Code/Cowork` → spawned Claude CLI + existing Claude hooks →
`Clawd /state` → session HUD/dashboard.

In parallel, an explicitly configured MCP tool calls the approval server:

`MCP tool` → `clawd_request_approval` → `Clawd /permission` → user decision →
the MCP tool resumes or fails closed.

The bridge uses a local loopback token generated by Clawd. The token is never
placed in Claude Desktop configuration, logs, or event payloads.

## Components

- `hooks/claude-desktop-bridge.js`: process discovery, PID/workspace
  resolution, session liveness, state posts.
- `src/claude-desktop-bridge-runtime.js`: main-process lifecycle and bridge
  configuration.
- `src/agent-registry.js` entry: desktop-specific label, capabilities, and
  focus support.
- `hooks/clawd-approval-mcp.js`: stdio MCP server implementing a fail-closed
  approval request tool for opted-in local automation.
- installer/doctor support: installs the bridge, optionally merges the MCP
  server into `claude_desktop_config.json`, and reports whether detection and
  approval transport are healthy.

## Safety and failure handling

- No Desktop binary patching, network interception, or private-store parsing.
- The approval MCP defaults to deny on timeout, unavailable Clawd, malformed
  input, or stale session.
- The bridge is state-only when process metadata cannot be resolved; it does
  not fabricate permission or completion events.
- Existing Claude CLI and Claude Desktop settings are merged, never replaced.
- Disabling the integration stops the bridge and removes only Clawd-marked MCP
  configuration.

## Acceptance checks

1. A real Code/Cowork process appears in the Clawd HUD as Claude Desktop.
2. Tool activity updates the displayed session state through existing hooks.
3. Process exit creates a single completion notification and cleans up.
4. HUD/dashboard focus activates Claude Desktop on macOS.
5. An opted-in MCP approval request produces a Clawd bubble; deny and timeout
   fail closed; allow resumes the caller.
6. A native Claude Desktop permission prompt remains native and works without
   the bridge.
